## Контекст

Приложение TimeCapsule (PHP 8.4, nginx, PHP-FPM, PostgreSQL 16) работает на одном экземпляре
`webserver` (`t3.micro`, Amazon Linux 2023, `eu-central-1`). Источник кода один: публичный репозиторий
`raetskijr-cloud/timecapsule` на GitHub. Новая версия выпускается одной и той же последовательностью
действий: получить код, установить библиотеки по `composer.lock`, создать недостающие таблицы,
перезагрузить PHP-FPM.

### Факторы решения

1. Однозначность версии: по серверу должно быть видно, какой коммит работает.
2. Повторяемость: последовательность шагов не должна зависеть от внимательности оператора.
3. Откат: возврат к предыдущей версии выполняется без правки файлов на сервере.
4. Безопасность: сервер читает репозиторий и не может в него писать; секреты (`.env`) остаются на сервере.
5. Трудоёмкость запуска: сколько действий нужно для одного выпуска.

## Решение

Выпуск выполняется скриптом `~/deploy.sh` (на сервере это ссылка на `bin/deploy.sh` из репозитория),
запускаемым с рабочего компьютера командой `ssh ... ./deploy.sh`. Скрипт работает в режиме
`set -euo pipefail`, нумерует шаги `[1/5]...[5/5]`, при ошибке называет строку сбоя, дописывает строку
в `~/deploy.log` и в конце печатает коммит, который теперь работает на сервере. Ключ `--dry-run` выполняет
только `git fetch` и показывает отличия, ничего не меняя.

## Рассмотренные альтернативы

Сравнивались три способа, обязательные по заданию. Критерии соответствуют пяти факторам выше.

| Критерий | `scp` | `git pull` вручную (вариант A) | `deploy.sh` (вариант B) |
| --- | --- | --- | --- |
| Однозначность версии | нет: набор файлов без истории | да: коммит | да: коммит, плюс строка в `deploy.log` |
| Повторяемость | низкая: список файлов определяет человек | средняя: 4-5 команд по памяти | высокая: порядок зафиксирован в файле |
| Откат | копирование прежних файлов, если они сохранены | `git revert`, `git push`, снова команды | `git revert`, `git push`, `./deploy.sh` |
| Безопасность | код живёт на ноутбуке, `vendor/` копируется целиком | сервер только читает репозиторий | то же, плюс остановка при первой ошибке |
| Трудоёмкость запуска | копирование нужных файлов, `vendor/` отдельно | вход по SSH и ввод команд | одна команда, вход на сервер не нужен |

Вариант `scp` отклонён из-за отсутствия истории и ненадёжного отката. Вариант A отклонён из-за риска
пропустить `composer install` или перезагрузку PHP-FPM. Системы CI/CD (GitHub Actions, AWS CodeDeploy)
в работе не рассматривались как реализуемые: они изучаются в последующих лабораторных работах.

## Последствия

### Положительные

- Версия на сервере определяется коммитом и видна в последней строке вывода.
- Откат выполняется через репозиторий и не требует ручных правок на сервере.
- Запуск с рабочего компьютера состоит из одной команды.

### Отрицательные

- Скрипт имеет один параметр запуска (`--dry-run`) и не проверяет работоспособность главной страницы после выпуска.
- Во время `git pull` файлы заменяются по одному, поэтому короткое время сервер может отдавать смесь старых и новых файлов.

### Риски

- Сломанный коммит попадает на сервер без проверки (подтверждено в Задании 13: `/health` отвечает `ok` при ошибке 500 на главной).
- Доступ по SSH ограничен адресом `My IP`; при смене адреса провайдера запуск с ноутбука блокируется до правки Security Group.
- Зависимость от доступности GitHub в момент выпуска.
