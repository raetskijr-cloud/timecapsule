## Контекст

В LR2 приложение TimeCapsule и PostgreSQL работали на одном экземпляре `webserver` в default VPC. В LR3 создана собственная сеть
`timecapsule-dev-vpc` с двумя публичными и двумя приватными подсетями. Нужно решить, где размещать базу данных.

### Факторы решения

1. Доступность базы из интернета: порт 5432 не должен быть достижим снаружи ни при какой ошибке одного фильтра.
2. Независимость жизненного цикла: пересоздание или замена сервера приложения не должна затрагивать данные.
3. Обновления и пакеты: как база получает обновления безопасности.
4. Стоимость в постоянной эксплуатации.
5. Сложность настройки и сопровождения.

## Решение

База размещается на отдельном экземпляре `timecapsule-dev-db` (`t3.micro`, Amazon Linux 2023) в подсети `timecapsule-dev-private-a`
(`10.14.10.0/24`) без публичного адреса. Подсеть не имеет маршрута в Internet Gateway. Входящий 5432 разрешён только от группы
`timecapsule-dev-web-sg`, SSH только от `timecapsule-dev-bastion-sg`. В `pg_hba.conf` допускается единственная строка
`host timecapsule timecapsule 10.14.0.0/24 scram-sha-256`. Приложение обращается к базе по имени `db.timecapsule.internal`
(приватная зона Route 53, запись A, TTL 60). Обновления устанавливаются через временный NAT Gateway, который поднимается и
убирается скриптами `scripts/nat-up.sh` и `scripts/nat-down.sh`.

## Рассмотренные альтернативы

| Критерий | A. База на сервере приложения (как в LR2) | B. Отдельный сервер в публичной подсети | C. Отдельный сервер в приватной подсети (выбрано) |
| --- | --- | --- | --- |
| Доступность из интернета | порт закрыт только Security Group; сервер приложения публичный | публичный адрес у сервера базы; защита держится на одном фильтре | публичного адреса и маршрута нет; три независимых механизма |
| Независимость жизненного цикла | нет: образ или удаление сервера затрагивает данные | да | да |
| Обновления и пакеты | прямой доступ в интернет | прямой доступ в интернет | только через временный NAT |
| Стоимость | один экземпляр | два экземпляра, лишний публичный IPv4 | два экземпляра; NAT только на время обновления |
| Сложность | минимальная | средняя | выше: bastion, приватная зона, NAT-скрипты |

Вариант A отклонён: данные и приложение теряются вместе, а любой эксплуатируемый дефект веб-сервера открывает доступ к базе на
том же узле. Вариант B отклонён: база получает публичный адрес, и безопасность определяется единственным правилом Security Group.

## Последствия

### Положительные

- Базу нельзя достичь из интернета: у экземпляра нет публичного IP, у подсети нет маршрута `0.0.0.0/0`.
- Сервер приложения заменяем: данные остаются на `db`, адрес базы задан именем `db.timecapsule.internal`.
- Отказ базы виден сразу: `/health` возвращает `"db":"error"` примерно через 5 с (таймаут PDO), после запуска приложение
  восстанавливается само, приватный адрес `10.14.10.165` сохраняется.

### Отрицательные

- Пакеты и обновления безопасности без NAT недоступны. Обновление требует временного NAT Gateway: около $0,05 в час и около $0,05
  за ГБ обработанного трафика (ставки региона `eu-central-1` ориентировочные, уточняются в калькуляторе AWS) плюс почасовая оплата Elastic IP шлюза; при работе 10-15 минут стоимость измеряется центами. Постоянный NAT стоил бы
  около $1,25 в сутки, поэтому не используется.
- Два экземпляра `t3.micro` вместо одного и дополнительный том 8 ГБ.

### Риски

- Забытый NAT Gateway или его Elastic IP. Смягчение: `nat-down.sh`, проверка `describe-nat-gateways` в конце занятия (runbook).
- Единственный `db` в зоне `eu-central-1a`: при отказе зоны база недоступна. Для переживания отказа зоны потребуются реплика
  в `private-b` (или Amazon RDS Multi-AZ), второй сервер приложения в зоне `b` и балансировщик нагрузки.
- Права на `.env` после правки: `sed -i` создаёт файл с группой `ec2-user`, PHP-FPM перестаёт читать настройки и применяет
  значения по умолчанию (см. отчёт, раздел 3.4). После правки нужно вернуть группу `apache`.

### Elastic IP у `app` и роль балансировщика

Публичный адрес `app` без Elastic IP меняется после каждой остановки и запуска, поэтому Elastic IP закрепляет адрес, указанный в
`APP_URL` и в браузере. У bastion постоянный адрес не нужен: администратор узнаёт его после запуска и обновляет `HostName`.
Elastic IP стоит $0,005 в час всегда, в том числе при остановленном сервере (около $3,6 в месяц). Когда перед серверами
появится Application Load Balancer, пользователи будут обращаться к его DNS-имени, а серверы получат только приватные адреса,
поэтому Elastic IP у `app` станет не нужен.
