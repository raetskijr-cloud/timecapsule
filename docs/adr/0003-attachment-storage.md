## Контекст

В LR2 и LR3 вложения капсул лежат в `storage/uploads` на диске EBS сервера `timecapsule-dev-app`. Пока сервер один, это работает,
но сервер нельзя заменить новым или запустить второй рядом: файлы пользователей есть только на одном диске.

### Факторы решения

1. Потеря данных при замене или отказе сервера приложения.
2. Работа с несколькими серверами за балансировщиком.
3. Защита от случайного и злонамеренного удаления.
4. Стоимость хранения и управляемость её роста.
5. Нагрузка на сервер при скачивании и объём изменений в коде.

## Решение

Вложения хранятся в бакете S3 `timecapsule-dev-uploads-danilaraetchi` под префиксом `uploads/`. Бакет закрыт для публичного доступа
(Block Public Access, ACL отключены), шифруется SSE-S3, версионирован; политика бакета запрещает запросы без HTTPS; правило
`timecapsule-dev-noncurrent` ограничивает историю версий. Приложение работает с бакетом через роль сервера
`timecapsule-dev-app-role` с политикой `timecapsule-dev-app-s3` (только `GetObject`, `PutObject`, `DeleteObject` под `uploads/*`;
версии удалять и список читать нельзя). Ключи доступа в `.env` не хранятся. Файл браузер получает по подписанному URL,
который приложение выдаёт после собственной проверки прав на капсулу.

## Рассмотренные альтернативы

| Критерий | A. Диск EBS сервера (как в LR2, LR3) | B. Amazon EFS | C. Amazon S3 (выбрано) |
| --- | --- | --- | --- |
| Замена сервера без потери файлов | нет: файлы на диске сервера | да | да |
| Несколько серверов за ALB | нет: у каждого свой диск | да, общая файловая система | да, общий бакет |
| Защита от удаления | только снимки EBS, которые нужно настраивать | резервные копии AWS Backup, версий файлов нет | версионирование и маркеры удаления |
| Стоимость роста | оплачивается весь том, даже пустой | около 0,33 USD за ГБ-месяц плюс цели монтирования в подсетях | оплачиваются только занятые ГБ, дешёвые классы и правила жизненного цикла |
| Нагрузка на сервер при скачивании | сервер читает и отдаёт каждый файл | то же, через NFS | браузер скачивает напрямую из S3 |
| Объём изменений в коде | нет | малый (монтирование, код не меняется) | замена одного модуля и SDK |

Вариант A отклонён: данные привязаны к серверу. Вариант B отклонён: решает общий доступ, но платная ёмкость выше, нужны цели
монтирования и NFS-трафик, а файлы всё равно отдаёт сервер приложения; версий объектов нет.

## Последствия

### Положительные

- Сервер хранит только код и настройки: его можно заменить, не потеряв вложений (проверено переносом `storage/uploads` в
  `~/uploads-backup`: приложение продолжает работать).
- Права минимальны: роль не видит список бакета и не может удалить версию. Злоумышленник с учётными данными роли может
  добавить маркер удаления, но предыдущие версии остаются и восстанавливаются.
- Скачивание идёт мимо сервера.

### Отрицательные и ограничения

- **Как пользователь получает файл.** Приложение проверяет права на капсулу и отвечает 302 на подписанный URL
  (`s3.eu-central-1.amazonaws.com/uploads/...?X-Amz-...`). Срок ссылки ограничивает параметр `X-Amz-Expires`: `PRESIGN_TTL_SECONDS`,
  по умолчанию 300 с; после срока S3 отвечает `AccessDenied` (`Request has expired`). Ссылку не нужно отзывать: она сама истекает,
  а ключ в ней изменить нельзя, так как подпись покрывает адрес.
- **Защита от удаления и рост стоимости.** От случайного удаления защищает версионирование (удаление добавляет маркер) и политика,
  не дающая `s3:DeleteObjectVersion`. Рост ограничивает правило `timecapsule-dev-noncurrent`: старые версии в Standard-IA через
  30 дней, удаление через 90 дней (с сохранением двух последних), незавершённые загрузки удаляются через 7 дней.
- Каждое скачивание требует подписи в приложении и обращения к S3; без интернета (без NAT или VPC endpoint) сервер в приватной
  подсети S3 не достанет. Для `app` в публичной подсети это не проблема.

### Несколько серверов и балансировщик

Серверы приложения станут взаимозаменяемыми: у всех одна роль, один бакет, ссылки подписываются любым из них и действуют
независимо от того, какой сервер их выдал. Локальных файлов и привязки пользователя к серверу не нужно. Роль придётся
вынести в шаблон запуска (instance profile), а серверам в приватных подсетях дать доступ к S3 через VPC endpoint.

### Риски

- Версии занимают место: правило жизненного цикла должно оставаться включённым.
- Бакет в одном регионе: при отказе `eu-central-1` вложения недоступны; нужна репликация в другой регион (Cross-Region Replication).
